# Security review — November 2026 (pre-launch)

Internal review of the whole codebase by the engineering team (not an external penetration test). Scope: tenant
isolation, authorization, secrets, webhooks, public endpoints, AI tool safety, browser security, privacy controls.

## Method

- Read through every migration's grants, RLS policies and SECURITY DEFINER functions.
- Read through every route handler, server action and proxy branch.
- New automated invariants (`tests/db/security-invariants.test.ts`), run in CI:
  - every public table has RLS;
  - anonymous users can call only `get_invitation_preview`, `health_check` and `widget_public_config`;
  - the `private` schema is closed to anonymous users;
  - every SECURITY DEFINER function pins its `search_path`;
  - server-only functions are not callable by signed-in users;
  - nobody but the service role can write admins, plans, settings, subscriptions or audit logs.
- CSP verified on a production build: `npm run check:csp`, plus a Chromium run with no violations.

## Controls in place (with tests)

| Area | Control |
|---|---|
| Tenant isolation | RLS on all tables, composite foreign keys `(business_id, id)`, membership checked in SQL; the browser's `business_id` is only a selector |
| Roles | `has_business_role()` in every mutating function; UI hides controls but does not enforce |
| Operator access | `platform_admins` writable only via SQL/service role; every `admin_*` function re-checks; actions audited; `/admin` returns 404 to others |
| Secrets | Service-role key, OpenAI, Resend, Paddle, Twilio and cron secrets are read only in server modules (`server-only`); `.env*` is git-ignored |
| Webhooks | Paddle signature (SDK) and idempotent, order-aware events; Twilio signature over the canonical URL; cron bearer compared in constant time |
| AI | No SQL from the model; Zod-validated tools; tenant ids come from the server; booking only after quote and confirmation in a later message; reply guard against invented confirmation numbers; prompt-leak canary; per-business and per-visitor rate limits; usage limits checked under a per-business lock |
| Browser | Nonce CSP (no inline scripts without nonce, no eval), `frame-ancestors 'none'` except the widget's listed sites, HSTS, nosniff, COOP, strict referrer; same-origin check on JSON APIs; server actions use Next.js's built-in origin check |
| Auth | Supabase Auth with email verification; `getClaims()` verifies JWTs; open-redirect-safe `next` handling |
| Privacy | Export, guest erasure, workspace deletion, retention jobs, hashed visitor and phone references, call transcripts without audio recording |

## Findings fixed in this phase

1. **Free trial could be obtained again by deleting a workspace** (trial grants were deleted along with it) → grants now
   survive deletion. Tested.
2. **The audit log would have been lost when a workspace is deleted** → the foreign key was dropped, so the log stays
   immutable and outlives the workspace.
3. **CI on GitHub had failed on every push since Phase 1** without being noticed (local checks passed); the typecheck step ran without the generated route types → the
   `typecheck` script now runs `next typegen` first.
4. **No CSP** (known gap since Phase 1) → nonce-based CSP.

## Accepted risks / follow-ups

| Risk | Severity | Note |
|---|---|---|
| Operator accounts have no MFA enforced | **Medium** | Use a strong unique password and few admins. Follow-up: Supabase MFA (TOTP) and require AAL2 in `require_platform_admin()` |
| No external penetration test | Medium | Recommended before scaling or before handling sensitive customers |
| Signed-in users can call the helper functions `private.stay_price`, `booking_setting` and `business_today` for any business id | Low | Needed by the availability search, which runs with the user's permissions. Reveals prices, settings or the local date only if the attacker knows another business's random UUIDs |
| `style-src 'unsafe-inline'`; any same-origin script file allowed | Low | See ADR 0012 |
| Trial abuse with new email addresses | Low | One trial per account; add signals (card, phone, domain) if abused |
| The error-alert throttle is kept in memory per server instance | Low | Bursts across many instances can send more alerts |
| No WAF or bot protection on sign-up | Low | Supabase Auth rate limits apply; add CAPTCHA (Supabase supports hCaptcha/Turnstile) if bots appear |
| Dependencies | Ongoing | Run `npm audit` and update monthly; enable Dependabot on GitHub |
